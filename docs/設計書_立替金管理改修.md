## 2. 課題整理

### 2.1 現行業務で不足している機能

| # | 課題 | 影響 |
|---|------|------|
| 1 | 取引登録時に「立替金」としての区分がない | どの支出が利用者への立替かを特定できない |
| 2 | 利用者別の立替金集計ができない | 請求書作成のたびに手作業で集計が必要 |
| 3 | 請求書発行機能がない | Excel等で別途作成している |
| 4 | 請求済み/未請求の管理ができない | 二重請求・請求漏れのリスク |
| 5 | 入金管理機能がない | 利用者からの入金を別帳簿で管理 |
| 6 | 拠点別の立替金集計・補充管理がない | 本部から拠点への資金補充額を手計算 |
| 7 | 月次締め機能がない | 締め後に過去データを変更されるリスク |
| 8 | 振込依頼・振込済み管理がない | 拠点への振込を別管理 |

### 2.2 運用上のリスク

- 立替金と通常経費の混在による集計ミス
- 月次請求の漏れ・遅延
- 拠点への補充金額の計算誤り
- 未収金の見落とし（一部入金・長期未収）
- 締め後の不正な修正

## 5. データモデル追加案

### 5.1 既存テーブル変更

#### Resident（利用者）テーブル拡張

```sql
ALTER TABLE residents ADD COLUMN
  billing_name TEXT,              -- 請求先名（利用者と異なる場合）
  billing_address TEXT,           -- 請求先住所
  billing_postal_code TEXT,       -- 請求先郵便番号
  billing_contact TEXT,           -- 請求先連絡先
  billing_notes TEXT;             -- 請求に関する備考
```

#### Location（拠点）テーブル拡張

```sql
ALTER TABLE locations ADD COLUMN
  bank_name TEXT,                 -- 銀行名
  bank_branch TEXT,               -- 支店名
  account_type TEXT,              -- 口座種別（普通/当座）
  account_number TEXT,            -- 口座番号
  account_holder TEXT;            -- 口座名義
```

#### Transaction（取引）テーブル拡張

```sql
ALTER TABLE transactions ADD COLUMN
  billing_status TEXT DEFAULT 'unbilled'
    CHECK (billing_status IN ('unbilled', 'billed', 'paid', 'partial', 'carried_over')),
  billing_id UUID REFERENCES billings(id),   -- 紐付き請求書
  billing_month TEXT;             -- 請求対象年月 (YYYY-MM形式)
```

### 5.2 新規テーブル

#### MonthlyClose（SV締め）

```sql
CREATE TABLE monthly_closes (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  location_id UUID NOT NULL REFERENCES locations(id),
  year_month TEXT NOT NULL,          -- 'YYYY-MM'
  status TEXT NOT NULL DEFAULT 'open'
    CHECK (status IN ('open', 'closed', 'modified')),
    -- open: 未締め
    -- closed: SV締め済み
    -- modified: 締め後に現場修正あり（SV再確認待ち）
  closed_by UUID REFERENCES employees(id),
  closed_at TIMESTAMPTZ,
  modification_count INTEGER NOT NULL DEFAULT 0, -- 締め後修正回数
  last_modified_at TIMESTAMPTZ,                  -- 最終修正日時
  last_modified_by UUID REFERENCES employees(id),
  last_modified_reason TEXT,                     -- 最終修正理由
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW(),
  UNIQUE(location_id, year_month)
);
```

#### Billing（請求書）

```sql
CREATE TABLE billings (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  billing_number TEXT NOT NULL UNIQUE,  -- 請求書番号 (自動採番)
  location_id UUID NOT NULL REFERENCES locations(id),
  resident_id UUID NOT NULL REFERENCES residents(id),
  year_month TEXT NOT NULL,             -- 請求対象年月 'YYYY-MM'
  billing_date DATE NOT NULL,           -- 請求日
  due_date DATE,                        -- 支払期限
  total_amount INTEGER NOT NULL,        -- 請求合計額
  paid_amount INTEGER NOT NULL DEFAULT 0,  -- 入金済み額
  status TEXT NOT NULL DEFAULT 'draft'
    CHECK (status IN ('draft', 'issued', 'sent', 'partial', 'paid', 'overdue', 'cancelled')),
  notes TEXT,
  created_by UUID NOT NULL REFERENCES employees(id),
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);

-- 請求明細（取引との紐付け）
CREATE TABLE billing_items (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  billing_id UUID NOT NULL REFERENCES billings(id) ON DELETE CASCADE,
  transaction_id UUID NOT NULL REFERENCES transactions(id),
  amount INTEGER NOT NULL,              -- 請求金額（取引金額と同額が基本）
  created_at TIMESTAMPTZ DEFAULT NOW()
);
```

#### Payment（入金）

```sql
CREATE TABLE payments (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  billing_id UUID NOT NULL REFERENCES billings(id),
  payment_date DATE NOT NULL,
  amount INTEGER NOT NULL,
  payment_method TEXT DEFAULT 'transfer'
    CHECK (payment_method IN ('transfer', 'cash', 'other')),
  notes TEXT,
  recorded_by UUID NOT NULL REFERENCES employees(id),
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);
```

#### Settlement（拠点精算）

```sql
CREATE TABLE settlements (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  location_id UUID NOT NULL REFERENCES locations(id),
  year_month TEXT NOT NULL,              -- 'YYYY-MM'
  total_advance_amount INTEGER NOT NULL, -- 月次立替合計
  total_payment_received INTEGER NOT NULL DEFAULT 0, -- 利用者からの入金合計
  replenishment_amount INTEGER NOT NULL, -- 補充必要額
  status TEXT NOT NULL DEFAULT 'pending'
    CHECK (status IN ('pending', 'requested', 'transferred', 'confirmed')),
  transfer_date DATE,                    -- 振込実行日
  transfer_amount INTEGER,               -- 実振込額
  transferred_by UUID REFERENCES employees(id),
  confirmed_by UUID REFERENCES employees(id),
  confirmed_at TIMESTAMPTZ,
  notes TEXT,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW(),
  UNIQUE(location_id, year_month)
);
```

### 5.3 ER図（追加分の関連）

```
Location ──┬── MonthlyClose (1:N, 月ごと)
           ├── Settlement (1:N, 月ごと)
           └── Billing (1:N)

Billing ──┬── BillingItem (1:N) ── Transaction (N:1)
```

## 6. 状態遷移

### 6.1 取引の請求ステータス

```
┌──────────┐    請求書作成     ┌──────────┐    全額入金     ┌──────────┐
│  unbilled │ ──────────────→ │  billed  │ ────────────→ │   paid   │
│  未請求   │                  │  請求済   │                │  入金済   │
└──────────┘                  └──────────┘                └──────────┘
                                   │
                                   │ 一部入金
                                   ▼
                              ┌──────────┐    残額入金     ┌──────────┐
                              │ partial  │ ────────────→ │   paid   │
                              │ 一部入金  │                │  入金済   │
                              └──────────┘                └──────────┘
                                   │
                                   │ 翌月繰越
                                   ▼
                              ┌──────────────┐
                              │ carried_over │
                              │   繰越       │
                              └──────────────┘
```

### 6.2 請求書ステータス

```
┌───────┐   確定    ┌────────┐   送付    ┌───────┐
│ draft │ ───────→ │ issued │ ───────→ │ sent  │
│ 下書き │          │ 発行済  │          │ 送付済 │
└───────┘          └────────┘          └───────┘
                                          │
                         ┌────────────────┤
                         │                │
                    一部入金           全額入金
                         ▼                ▼
                   ┌──────────┐     ┌──────────┐
                   │ partial  │ ──→ │  paid    │
                   │ 一部入金  │     │ 入金済    │
                   └──────────┘     └──────────┘

        ※ 期限超過で自動的に overdue に遷移
        ※ 取消は cancelled
```

### 6.3 拠点精算ステータス

```
┌──────────┐   振込依頼    ┌────────────┐   振込実行    ┌──────────────┐   確認    ┌────────────┐
│ pending  │ ───────────→ │ requested  │ ───────────→ │ transferred  │ ──────→ │ confirmed  │
│ 集計中   │              │ 振込依頼済  │              │  振込済      │         │  確認済     │
└──────────┘              └────────────┘              └──────────────┘         └────────────┘
```

### 6.4 SV締め（月次締め）ステータス

※ 元の出納帳の「SV締め」を踏襲した設計。
締め＝「SVが内容を確認・承認した」という意味であり、完全ロックではない。
締め後も現場での修正は可能だが、修正理由の入力が必須となり、監査ログに自動記録される。

```
┌───────┐    SV締め実行    ┌────────┐
│ open  │ ──────────────→ │ closed │
│ 未締め │                 │ SV締め済│
└───────┘                 └────────┘
                               │
                               │ 現場で修正発生
                               │ （修正理由必須＋監査ログ記録）
                               ▼
                          ┌──────────────┐    SV再締め    ┌────────┐
                          │ modified     │ ────────────→ │ closed │
                          │ 締め後修正あり│               │ SV締め済│
                          └──────────────┘               └────────┘
```

**締め後の編集ルール:**
- 締め後も現場スタッフは取引の登録・編集が可能
- ただし、締め済み月のデータを変更する場合:
  1. 「SV締め済みの月です」という警告が表示される
  2. 修正理由の入力が必須となる
  3. 修正内容は監査ログに自動記録される
  4. MonthlyCloseのステータスが「modified（締め後修正あり）」に自動変更
  5. SVが再確認後、再度「closed」に戻す
- この運用により、現場の柔軟性を維持しつつ、変更の追跡性を確保する

## 7. 月次業務フロー

### 7.1 全体フロー（毎月の流れ）

```
月初〜月末: 日常業務
─────────────────────────────────────────────────────────
  [現場] 利用者への立替支出が発生
    → 取引登録（立替金 / 利用者紐付け）
    → 承認ワークフロー（既存機能）
    → 金種確認（既存機能）

月末〜翌月初: 月次処理
─────────────────────────────────────────────────────────
  Step 1. 月次締め前チェック
    ├── 未承認取引の確認・処理
    ├── 立替金の請求対象月確認
    └── 金種確認の実施

  Step 2. SV締め実行
    ├── SVが対象月の内容を確認・承認
    ├── ステータスを「SV締め済み」に変更
    └── ※締め後も現場修正は可能（修正理由必須＋監査ログ記録）

  Step 3. 利用者別請求書作成
    ├── 未請求の立替取引を利用者別に自動集計
    ├── 請求書プレビュー・確認
    ├── 請求書確定・発行
    └── PDF出力・送付

  Step 4. 拠点別精算
    ├── 拠点ごとの月次立替合計を自動集計
    ├── 利用者からの入金額を差し引き
    ├── 補充必要額を算出
    ├── 振込依頼書出力
    └── 本部からの振込実行・記録

  Step 5. 入金管理（随時）
    ├── 利用者からの入金を記録
    ├── 請求書と入金の突合
    ├── 一部入金の場合は残額管理
    └── 未収管理・督促

  Step 6. 翌月繰越
    └── 未収分を翌月に繰り越し
```

### 7.2 請求書作成フロー（詳細）

```
1. 管理者が「請求管理」画面を開く
2. 対象年月を選択
3. 「請求書一括作成」を押下
4. システムが以下を自動処理:
   a. 対象月の承認済み立替取引を取得
   b. 利用者別にグルーピング
   c. 各利用者について請求書ドラフトを生成
   d. 前月繰越分があれば合算
5. 管理者が各請求書を確認・修正
6. 「発行」で確定
7. PDF出力・印刷・送付
8. 対象取引のbilling_statusを「billed」に更新
```

### 7.3 拠点精算フロー（詳細）

```
1. 本部管理者が「拠点精算」画面を開く
2. 対象年月を選択
3. 各拠点について自動算出:
   a. 月次立替合計（承認済みの立替取引合計）
   b. 利用者からの入金合計
   c. 補充必要額 = 立替合計 − 入金合計
4. 管理者が確認し「振込依頼」を実行
5. 振込依頼書をCSV/PDF出力
6. 実際の振込後、「振込済み」を記録
7. 拠点側で入金確認後「確認済み」に更新
```

## 10. 実装上の方針

### 10.1 既存コードへの影響を最小化

- 既存の `Transaction` 型にフィールド追加（破壊的変更なし）
- 既存画面は条件分岐による拡張（リプレースしない）
- 新機能は新規ページ・コンポーネントとして追加
- 既存のZustand store / hooks パターンを踏襲

### 10.2 デモモード対応

- 新規テーブルに対応するデモデータを `demoStore.ts` に追加
- Supabase接続なしでも全機能をテスト可能にする

### 10.3 UI方針

- 既存のTailwind CSSテーマ・コンポーネントスタイルを踏襲
- 新規画面も既存のレイアウト（AppShell）内に配置
- モバイル対応を維持（現場での利用を想定）
- 請求書関連はデスクトップ中心でも可（管理者業務）

### 10.4 権限設計

## 付録: 型定義案（TypeScript）

```typescript
// 請求ステータス（取引に追加）
type BillingStatus = 'unbilled' | 'billed' | 'paid' | 'partial' | 'carried_over';

// 請求書ステータス
type InvoiceStatus = 'draft' | 'issued' | 'sent' | 'partial' | 'paid' | 'overdue' | 'cancelled';

// 精算ステータス
type SettlementStatus = 'pending' | 'requested' | 'transferred' | 'confirmed';

// SV締めステータス
type MonthlyCloseStatus = 'open' | 'closed' | 'modified';

// 入金方法
type PaymentMethod = 'transfer' | 'cash' | 'other';

// SV締め
interface MonthlyClose {
  id: string;
  location_id: string;
  year_month: string;
  status: MonthlyCloseStatus;
  closed_by: string | null;
  closed_at: string | null;
  modification_count: number;
  last_modified_at: string | null;
  last_modified_by: string | null;
  last_modified_reason: string | null;
  created_at: string;
  updated_at: string;
}

// 請求書
interface Billing {
  id: string;
  billing_number: string;
  location_id: string;
  resident_id: string;
  year_month: string;
  billing_date: string;
  due_date: string | null;
  total_amount: number;
  paid_amount: number;
  status: InvoiceStatus;
  notes: string | null;
  created_by: string;
  created_at: string;
  updated_at: string;
  // Relations
  resident?: Resident;
  location?: Location;
  items?: BillingItem[];
  payments?: Payment[];
}

// 請求明細
interface BillingItem {
  id: string;
  billing_id: string;
  transaction_id: string;
  amount: number;
  created_at: string;
  // Relations
  transaction?: Transaction;
}

// 入金
interface Payment {
  id: string;
  billing_id: string;
  payment_date: string;
  amount: number;
  payment_method: PaymentMethod;
  notes: string | null;
  recorded_by: string;
  created_at: string;
  updated_at: string;
}

// 拠点精算
interface Settlement {
  id: string;
  location_id: string;
  year_month: string;
  total_advance_amount: number;
  total_payment_received: number;
  replenishment_amount: number;
  status: SettlementStatus;
  transfer_date: string | null;
  transfer_amount: number | null;
  transferred_by: string | null;
  confirmed_by: string | null;
  confirmed_at: string | null;
  notes: string | null;
  created_at: string;
  updated_at: string;
  // Relations
  location?: Location;
}
```
